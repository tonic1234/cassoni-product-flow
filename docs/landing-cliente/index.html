Cassoni — Automatización SEO

Pipeline de optimización SEO para catálogo de productos de lujo

Sistema automatizado que extrae la ficha completa de productos desde WooCommerce, identifica keywords de alto volumen mediante Search Console y DataForSEO, y las incorpora en H1 y descripciones con validación por LLM.

Qué construimos.

(02.1) — El flujo del agente en detalle

Cómo trabaja el agente, paso a paso.

Cada ficha recorre una cadena de 11 etapas. Las fuentes de datos son reales (WooCommerce, Google Search Console, DataForSEO), las reglas que deciden son deterministas y verificables —el LLM solo escribe— y ninguna edición llega a producción sin pasar el gate.

01–02

Entrada y extracción

La lista de URLs se convierte en slugs. Solo se procesan productos publicados (los drafts se saltean).

03–04

Datos reales

GSC trae las keywords con posición/impresiones (y su oportunidad); DataForSEO filtra por volumen con bulking y dedup global.

05–06

Reglas, no opiniones

Anti-canibalización contra datos reales (H1 de hermanas, categorías de la tienda) y una sola keyword por palabra compartida.

07–08

Escribir, validar

El LLM edita H1 + long sobre el texto actual (conservación ≥80%). El validador primero corre reglas duras en código, después el LLM.

09–10

Gate y escritura

Nada se publica sin gate. En dry-run el pipeline corre completo y no toca nada; el write exige validez + aprobación.

11

Traza y ritmo

Cada decisión queda en la DB (antes/después, motivos, costos). El scheduler trabaja 9–18 con cargas variables, sin patrones detectables.

La prueba real — Connor Sofa by Borzalino

Se corrió el agente sobre una ficha real de cassoni.com, en frío (sin escribir nada en el sitio):

🔹 H1: Borzalino Connor Sofa · long description: 87 → 167 palabras, conservación del original: 100%.

🔹 Secundarias con palabras distintas y porqué anclado en atributos reales · gate mecánico: 0 issues.

🔹 Se detectó y corrigió un bug real (tope de tokens del razonador) con su test de regresión.

EN SIMPLE

Es un redactor SEO virtual que trabaja de 9 a 18 sin que Google lo distinga de una persona. Lee cada ficha, busca las palabras correctas con fuentes reales, decide con reglas fijas (no con corazonadas), reescribe solo lo mínimo indispensable, y nada se publica sin pasar un control doble. Todo queda anotado: qué cambió, por qué y cuánto costó.

Estado de la implementación: etapas 01–10 implementadas y testeadas (113 tests en suite, evidencia RED/GREEN en el repo). Pendientes para producción: key de WooCommerce con permisos, verificar acceso GSC, despliegue a CASE y el expansor (etapa señalada con *).

(03) — Componentes

Cada pieza en detalle.

01 · Extractor de URL a Slug

Script Python que procesa cualquier URL de WooCommerce y determina si es producto, categoría o etiqueta. Soporta múltiples idiomas (español, inglés, portugués, francés), URLs con query params, pretty permalinks, y estructuras custom. Si no puede determinar el tipo, lo reporta explícitamente.

Endpoint: /wp-json/wc/v3/products?slug={slug} · Auth: Consumer Key + Secret (Basic)

02 · WooCommerce API — Ficha Completa

Con el slug, consulta la REST API de WooCommerce y obtiene el objeto JSON completo: nombre, descripción (HTML), short_description, precio, SKU, categorías, tags, imágenes, atributos, variaciones, meta_data, dimensiones, stock, y más. Para productos variables, también extrae todas las variaciones con sus precios y atributos.

Campos clave: name (H1 actual) · description (HTML) · permalink · categories[]

03 · Google Search Console API

Para cada producto, consulta las top 10 keywords por las que esa URL recibió impresiones en los últimos 12 meses. Usa OAuth 2.0 para autenticarse contra la propiedad de Cassoni en Search Console. La API permite hasta 50.000 filas de datos por día, más que suficiente para procesar los 11.000 productos del catálogo.

Costo: $0 (gratuito) · Límite: 50.000 filas/día · Endpoint: /webmasters/v3/sites/{site}/searchAnalytics/query

04 · DataForSEO — Filtro por Volumen de Búsqueda (Técnica de Bulking)

GSC devuelve 10 keywords por producto → ~110.000 keywords total (11.000 productos × 10). Pero muchas se repiten entre productos similares.

¿Por qué no son 110.000 keywords únicas?
Imaginá 5 sofás distintos en el catálogo. GSC devuelve para cada uno:
Sofá A: "sofá de lujo", "sofá milano", "sofá cuero negro", "comprar sofá", "cassoni", ...
Sofá B: "sofá de lujo" , "sofá parís", "sofá terciopelo", "comprar sofá" , "cassoni" , ...
Sofá C: "sofá de lujo" , "muebles de diseño", "sillones modernos", "cassoni" , ...

Patrón: términos de categoría y marca se repiten en decenas o cientos de URLs. Solo los long-tail específicos ("sofá milano cuero negro") son realmente únicos.
Resultado: de 110.000 keywords, tras deduplicar quedan entre 20.000 y 40.000 únicas (~65-80% de solapamiento). El número exacto depende de la diversidad del catálogo y se conocerá al procesar los datos reales de Cassoni.

Se realiza una deduplicación con trazabilidad: cada keyword única mantiene una lista de las URLs de origen, para poder re-mapear los volúmenes a cada producto después del bulk.

Técnica de bulking: DataForSEO permite enviar hasta 1.000 keywords en un solo request HTTP. La API cobra $0,0095 por keyword (validado con datos reales: 19 keywords consumieron $0,18). El bulking no reduce el costo por keyword, pero sí la velocidad: en lugar de 30.000 llamadas individuales, consolidamos todo en 30 requests de 1.000. La API devuelve los volúmenes en el mismo orden del array de entrada, lo que permite re-mapear cada volumen a su keyword y de vuelta a los productos de origen.
Peor caso (40.000 únicas): $380.
Caso esperado (30.000 únicas): $285.
Es el componente más caro del proyecto y el costo dominante del pipeline.

En el pipeline, para cada producto se filtran hasta 10 keywords entre las que devolvió GSC, descartando nombres de marca y términos irrelevantes para mobiliario de lujo. Las que quedan se incorporan en H1 (la más descriptiva) y descripción (el resto).

Endpoint: /v3/keywords_data/google_ads/search_volume/live · Flujo: GSC por URL → keyword + URL mapping → deduplicar preservando origen → DataForSEO bulk (1.000/req) → resultados mapeados de vuelta a cada producto

05 · LLM Editor — Optimización de H1 y Descripción

El LLM recibe el H1 actual y la descripción larga existente, más las keywords seleccionadas. Debe:

  • Elegir la keyword más descriptiva del producto para el H1
  • Insertarla de forma natural y coherente sin forzar
  • Incorporar las keywords restantes en la descripción larga
  • Preservar el tono de lujo de Cassoni
  • No repetir conceptos que ya estaban en el texto original
  • Mantener el HTML y formato existentes

Modelo sugerido: Gemini 2.5 Flash (~$15,40 para 11K productos como editor). Ver comparativa completa en sección 09.

06 · Agente Validador

Un segundo LLM —o el mismo con un prompt de validación— revisa cada output: coherencia del texto, tono de lujo preservado, keywords efectivamente incorporadas, ausencia de repetición, y que el H1 siga siendo descriptivo del producto. Si detecta problemas, rebota el texto al editor para una segunda pasada.

Ritmo: ~50 productos/día procesados. Cada tanto, el equipo SEO revisa manualmente.

07 · Base de Datos de Trazabilidad

Cada producto procesado registra: URL, slug, keywords obtenidas de GSC, volumen de cada una vía DataForSEO, cuáles se seleccionaron y por qué, dónde se insertaron (H1 o descripción), el texto antes y después, y el resultado de la validación. Esto permite auditoría completa, iteración sobre decisiones pasadas, y demostración de impacto SEO.

(05) — Implementación

Fases del proyecto.

Fase 1 — Setup

Verificar credenciales de WooCommerce API (ya disponibles vía equipo SEO). Validar acceso OAuth a Google Search Console (ya configurado). Activar cuenta DataForSEO (plan Light ~$50/mes). Script extractor de URL → slug.

Fase 2 — Extracción (Staging)

Conectar WooCommerce API contra el sitio de staging de Cassoni (idéntico a producción). Procesar un lote piloto de 10-20 productos sin riesgo. Validar que la ficha JSON contiene todos los campos necesarios. Script de extracción de GSC para top 10 keywords.

Fase 3 — Keywords

Integrar DataForSEO para filtrar volumen. Afinar la lógica de descarte (marcas, términos genéricos, keywords no relevantes para lujo). Definir criterio de selección de la keyword principal para H1.

Fase 4 — LLM + Validación

Integrar el LLM editor (Gemini Flash) y el agente validador (Claude Sonnet). Nosotros definimos y ajustamos los prompts junto con el equipo de Cassoni; conectamos las APIs y armamos la interfaz para que puedan iterar sin tocar código. Procesar lote piloto con revisión del equipo SEO.

Fase 5 — Escala + Cron

DB de trazabilidad. Procesamiento del catálogo completo (11.000 productos) desde staging, con migración controlada a producción cuando esté validado. Cron en horario de oficina con intervalos variables (9-18 horario local, pausas aleatorias entre requests) para evitar que Google detecte automatización y penalice el sitio.

(06) — Cron

Ejecución anti-bot.

Por qué en horario de oficina con intervalos variables

Google detecta patrones de actualización masiva de contenido y puede interpretarlos como manipulación automatizada de SEO, lo que deriva en penalizaciones en el ranking. Un flujo constante de 11.000 productos editados en secuencia a las 3 AM es una firma clara de automatización. En cambio, ediciones espaciadas aleatoriamente durante el horario comercial (9:00–18:00, horario local) son indistinguibles del ritmo de trabajo de un equipo editorial humano. El objetivo es que Google vea un sitio con contenido que mejora orgánicamente, no un sitio siendo optimizado por un bot.

Ventana horaria

Lunes a viernes, 9:00–18:00 (horario local).
Sin ejecución fines de semana ni madrugada.
Si un producto queda pendiente, se retoma al día siguiente.

Intervalos variables

Tiempo aleatorio entre productos: 30s–5min.
Simula el ritmo de un redactor humano: a veces edita rápido, a veces se toma un café entre producto y producto.
Distribución no uniforme para evitar patrones detectables.

Volumen diario

Ritmo fijo: 50 productos/día.
Catálogo completo (11.000) en ~220 días hábiles.

Implementación

Cron con agente supervisor integrado.
random.uniform(30, 300) segundos entre productos.
Solo ejecuta en horario hábil (9-18 horario local, lun-vie).
Google ve ediciones a ritmo humano, no un bot.

(08) — Por qué Python

Por qué Python + Cron y no n8n.

Cassoni ya tiene un workflow de SEO en n8n (33 nodos, 119K imágenes procesadas). Para aquel proyecto, n8n fue la herramienta correcta: un flujo lineal de transformación de datos. Este proyecto es distinto. Estos son los motivos técnicos.

1. Esto no es un workflow — es un scheduler

n8n ejecuta workflows: disparador → pasos secuenciales → fin. Este proyecto necesita un planificador que corra durante meses, con pausas aleatorias, ventanas horarias, reanudaciones automáticas, y rate limiting coordinado entre 3 APIs distintas. Eso es un cron con lógica de scheduling, no un workflow.

2. Bulking: acumular antes de enviar

La técnica de bulking de DataForSEO requiere acumular keywords de múltiples productos antes de hacer un solo request de 1.000. n8n procesa items de a uno; no tiene un mecanismo nativo para "juntá 1.000 y después mandá". En Python es un array y un contador.

3. Trazabilidad con SQL real

Cada decisión del pipeline queda registrada en PostgreSQL: qué keyword, qué URL, qué volumen tenía, por qué se eligió, dónde se insertó, texto antes y después, resultado de la validación. n8n puede loguear en JSON, pero consultar "mostrame todas las keywords descartadas por ser marcas" requiere SQL.

4. Agente supervisor 24/7

El pipeline no corre solo: un agente LLM monitorea cada ejecución. Si algo falla —GSC sin datos, DataForSEO timeout, LLM responde incoherencias— envía un correo al equipo con el diagnóstico exacto: qué producto, qué paso falló, por qué, y si ya se salteó automáticamente. n8n puede disparar un webhook, pero no redactar un email diciendo "el producto #237 no tiene datos en GSC, es esperable para productos nuevos, lo salteé y seguí".

5. Versionado con git

Cada cambio en la lógica del pipeline es un commit: qué se modificó y por qué. Si el equipo de SEO dice "volvé a la versión de la semana pasada que funcionaba mejor", es un git revert. n8n tiene historial de versiones pero está atado a la UI y no sobrevive a migraciones o cambios de entorno.

6. Evolución sin límites de canvas

Cuando el equipo de SEO pida "agreguemos otra fuente de keywords" o "cambiemos el criterio de selección de 3 a 5", en Python es código nuevo + deploy. En n8n es arrastrar nodos en un canvas que ya tiene 33, con el riesgo constante de romper una conexión invisible. A escala de 11.000 productos y meses de operación, el código es más mantenible que un diagrama.

n8n fue la herramienta correcta para el proyecto anterior

El workflow de 33 nodos para generar meta descriptions de 119K imágenes era un flujo de transformación: imagen → clasificación → generación → validación. Ahí n8n brilló porque cada item sigue el mismo camino lineal. Este proyecto es un scheduler de largo plazo con bulking, rate limiting coordinado, y una DB relacional de trazabilidad. Para eso, Python + PostgreSQL + Cron es la infraestructura correcta.

(10) — Roadmap

Estimación de desarrollo.

La estructura de datos de WooCommerce de Cassoni ya la conocemos (procesamos 7.800 productos en el proyecto anterior de SEO). Credenciales ya disponibles. Las 4 APIs involucradas están maduras, tienen librerías Python listas para usar, documentación exhaustiva y ejemplos de código funcionales.

Validación de APIs

WooCommerce: wrapper Python oficial (wc-api-python). Fetch de producto en 5 líneas.
GSC API: Google provee guías completas con código Python listo para copiar. Método searchanalytics.query() con filtro por page para extraer keywords por URL. Autenticación vía OAuth2 o service account.
DataForSEO: endpoint bulk de 1.000 keywords/request. Basic Auth (base64). Documentación con ejemplos en curl y Python.
LLMs (Gemini, Claude, GPT): todos usan endpoints OpenAI-compatible. Mismo formato, mismo cliente HTTP.
Conclusión: las 4 APIs se conectan en horas, no en días. El trabajo real está en el orquestador, la trazabilidad y los fallbacks — no en la integración.

Día 3 — Pipeline completo procesando URLs reales

Día 1: credenciales + WooCommerce (fetch de ficha desde staging) + schema DB trazabilidad (qué keywords, qué URL, qué volúmenes, qué decisión).
Día 2: GSC (OAuth + top 10 keywords) + DataForSEO (volumen) + cron variable (9-18 horario local, intervalos aleatorios 30s-5min).
Día 3: conexión LLM + orquestador + validador. El pipeline procesa URLs reales, registra cada decisión en la DB, y corre en horario de oficina con timing humano.

Días 4–7 — Fallbacks, control de calidad, primer lote

Fallbacks: qué pasa si GSC no tiene datos para esa URL, si DataForSEO falla, si el LLM devuelve texto inválido. Degradación elegante, reintentos, logs.
Primer lote real: procesar 10 productos en staging, entregar resultados al equipo de SEO para validación de contenido.
Documentación: guía de operación, cómo leer la trazabilidad, cómo cambiar prompts sin tocar código.
